# 2026-08-06：行情降级模式与决策账本对账

## 触发背景

早报运行时，基金净值 HTTPS 数据可用，但全球行情现拉链路失败；数据库里的 AI、港日韩、加密和美债快照分别停在 8/1–8/4。同时：

- `actual_holdings.json` 明确记录 用户 已于 8/3 对 020274 加仓 5,000 元；
- `decisions` / `get_pending_decisions()` 仍把同方向建议列为待决策；
- 近 7 日 12 行、近 14 日 48 行含同日重复运行和重复建议，原始行数不等于“未采纳次数”；
- `get_rule_stats()` 的线上回填胜率与 10 年回测结果口径不同，例如 NDX_FED_01 线上统计与历史回测可显著冲突；
- 012752 的最新 NAV 日期为 8/4，另外三只为 8/5，不能直接把四个“单日涨幅”做等权平均。

## A. 行情数据降级模式（Degraded Market Data Mode）

### 1. 每段单独做新鲜度判定

报告不能只写一个总“数据基准日”。对基金、港股、日股、韩股、美股、AI、加密、美债分别记录：

- `as_of`：数据对应的市场日期/时间；
- `source`：现拉、数据库、代理 ETF 或其他来源；
- `freshness`：`fresh` / `previous_session` / `stale` / `missing`。

### 2. 陈旧快照只能作为“背景”，不能伪装成“今日行情”

现拉失败时可以读取数据库兜底，但必须：

- 标明具体日期，例如“AI（8/1 旧快照）”；
- 放在“历史背景/旧快照”语境；
- 不据此声称“今日领涨/今日主线”；
- 不基于旧快照给新的追涨、加仓或减仓动作；方向建议自动降级为持有/观察并列恢复条件。

### 3. 同日期闸门（Same-Date Gate）

以下计算只有在所有输入对应同一有效市场日（或明确做过汇率、时区、QDII 滞后对齐）时才允许：

- 四只持仓“等权单日涨幅”；
- 持仓组合 vs QQQ / SMH / KWEB 相对强弱；
- 港/日/韩/美股的横向强弱排序；
- 候选与现有持仓的当日超额收益。

若 NAV 日期不同（尤其 QDII T+1/T+2）或基准日期不同，禁止求平均；只逐只展示“数值 + 日期”，并写“日期未对齐，组合/相对强弱不可比”。

**硬性渲染闸门（2026-08-06 晚报复盘强化）**：

- 禁止“先算出组合均值/相对强弱，再补一句不可比”。免责声明不能挽救一个本就不该生成的数字。
- 只有 `all(as_of_i == comparison_as_of)`（或存在经验证的跨市场对齐映射）时，才创建聚合字段；否则字段应为 `None`，渲染为“日期未对齐，暂不计算”。
- QDII NAV、国内 ETF NAV、美国 ETF 收盘价不能仅因都叫“单日涨跌”就直接等权；必须先处理 T+1/T+2、时区和汇率口径。

```python
def same_date_metric(points):
    dates = {p.get("as_of") for p in points if p.get("value") is not None}
    if len(points) == 0 or len(dates) != 1 or any(p.get("value") is None for p in points):
        return None
    return sum(p["value"] for p in points) / len(points)
```

报告自检应搜索并拒绝这类反模式：`“均值/跑赢/落后/相对强弱 + 日期未对齐”`。若日期未对齐，前半句数字必须删除，而不是保留后再解释。

### 4. 降级输出最小模板

```text
📌 数据状态：基金截至 8/4–8/5；全球现拉不可用；DB 快照截至 8/1–8/4。
- 基金：逐只显示 NAV 日期，不计算组合单日平均。
- 全球市场：仅作带日期背景，不称“今日”。
- 相对强弱：日期未对齐，暂不计算。
- 策略：所有依赖缺失实时价格的动作降级为持有/观察；列数据恢复后的触发器。
```

## B. `actual_holdings` 与 `decisions` 对账

### 1. 事实优先级

判断是否采纳时按以下顺序：

1. `actual_holdings.json` 中带 用户 原话/成交说明的 `source`、金额变化和 `last_sync_with_patrick`；
2. `decision_tracker.apply_decision()` 已标记的执行记录；
3. `decisions` 原始待决策行。

若持仓文件明确记录成交，而 decisions 尚未回写，报告必须写：

> “实际已采纳；决策账本待对账。”

禁止写“0 采纳”或把该标的继续计入未采纳警报。

### 2. 原始 pending 行数不等于未采纳次数

报告前先按以下维度去重：

- 标的代码；
- 方向（add/reduce/hold/observe）；
- 同一自然日或同一次 cron 运行；
- 相同 `signal_ids` / 触发规则。

同日重复运行产生的多行只算一个“建议 episode”。重复的 observe 也不能被描述成多次未采纳动作。

### 3. 回写原则

- 若成交与某一建议可唯一匹配：调用 `apply_decision(decision_id, execution_note)`；
- 若存在多个重复 add 行，不能任意挑一个声称全部执行；先报告账本不一致，按“最近一次成交前、同标的同方向的有效建议”对账，并将其余重复项视为重复/被后续状态覆盖；
- 对账完成前，报告以持仓事实为准，同时披露 ledger mismatch。

## C. 两套胜率必须分命名空间

### 1. 历史回测统计

来源：`references/rule-backtest-results.md` / `backtest-truth-table.md`。

写法：

> “10 年回测：19 次，胜率 84.2%。”

用于判断规则历史有效性，但不等于线上实盘表现。

### 2. 线上回填统计

来源：`get_rule_stats()`，依赖 signals/decisions 的实际回填质量。

写法：

> “线上回填：43 次触发，已验证样本胜率 0%；大量待回填。”

不得把 `trigger_count` 当成已验证样本数，也不得与回测次数拼成同一指标。

### 3. 冲突处理

若历史回测强、线上回填弱或样本质量异常：

- 同时列两套口径；
- 检查验证覆盖率、重复信号和非交易日缺口；
- 在查清前把动作降级为观察/小仓验证，不用其中一套覆盖另一套。
